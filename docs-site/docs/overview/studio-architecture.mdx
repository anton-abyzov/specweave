# One ecosystem, three distinct jobs

**SpecWeave** keeps project intent and evidence in your repository. **vskill and Skill Studio** help you install and evaluate skills. **SpecWeave Studio** is the workspace on top: projects with a coordinator and workers on any provider, across your machines. Start with [the Studio overview](/docs/overview/studio/) for what it does; this page covers how the pieces connect.

<ProductMap />

SpecWeave Studio is not the app launched by `npx vskill studio`. That command opens **Skill Studio**, the skill development and evaluation workspace.

## The architecture

<Architecture />

| Layer | Responsibility | Boundary |
| --- | --- | --- |
| Browser | Display sessions, output and approvals | Browser connection state does not grant execution authority |
| Network route | Local network, an SSH tunnel, or Tailscale Serve to the selected host | Reaching a host is not permission; Studio still requires pairing on every route |
| Studio runtime | Own host-local sessions, accounts, admission and recovery | Pair each host separately; do not copy credentials between accounts |
| Native agent | Execute a turn through its selected provider/account | Provider availability and approval rules still apply |
| Repository | Code, specs, task ledger and verification evidence | Git transports project changes; it is not a shared live session database |
| vskill | Inspect/install skills and run evaluations | Source trust and evaluation results require independent assessment |

### Connecting other machines

Tailscale is not required. A Studio host can be reached in any of these ways, and one machine can keep several routes, using the first that answers:

| Route | When to use it | What you need |
| --- | --- | --- |
| Local network | The machines share a home or office network | Turn on network access on the host and pair with a one-time link |
| SSH | You can already SSH to the machine | The desktop app opens the tunnel and can start Studio on the remote host |
| Tailscale HTTPS | You are away from that network, or you want phone access | Both devices in the same tailnet; Tailscale Serve, never Funnel |

Tailscale **Serve** exposes a local service inside the private tailnet. **Funnel** is a different feature for public exposure; it is not the pilot's remote-access design. See the [official Tailscale Serve documentation](https://tailscale.com/docs/features/tailscale-serve). A hosted relay exists in the source but is turned off in the pilot.

### Providers and switching

Studio runs each provider's own agent (Claude Code, Codex, OpenCode, Cursor, Pi) with the sign-ins already on that machine. Each thread picks its provider, model and effort. You can change provider inside a thread: Studio passes a budgeted selection of the conversation to the new agent, which continues in the same checkout. Studio does not yet switch on its own when a provider reaches a usage limit; the limit banner offers to wait for the reset or check again.

### Optional components

**CLIProxyAPI** is optional. Studio can read pooled account usage from a CLIProxyAPI hub you already run and show it under **Usage → Limits**. Native Claude Code and Codex turns never pass through it. Routing personal subscription sign-ins through a shared proxy can conflict with a provider's terms, so check them before pooling accounts. **AnyModel** is likewise optional and only matters for API or local-model compatibility work.

### Where data goes

Local-first describes where project files and runtime state live. It does not mean every request stays on the machine. Native coding agents and Skill Studio evaluations can contact their configured cloud model providers. Review those providers, account policies and any tools your skills invoke before using sensitive material.

Keep live worktrees, session databases and credential stores on their owning hosts. Use git and explicit handoff for portable code and task state. Private network access and Studio pairing are complementary controls, not interchangeable credentials.

### Inside a Studio host

The client sends authenticated, typed commands to the runtime on the machine that owns the session. A database transaction records events, projections, receipts and pending side effects in an outbox. Workers perform native-provider and Git operations and record their outcomes. **An accepted command is not the same as a completed side effect.**

Session state belongs to the native runtime; SpecWeave remains responsible for project intent, task ownership and acceptance evidence. An account pin and the session's host affinity remain meaningful even when several machines share a subscription. Adding hosts does not create extra provider quota.

The optional [Jev / Decisions integration](/docs/guides/jev-system-one) handles bounded classifications in SpecWeave. Its model output is advisory: it does not grant permissions or prove a task passed verification.

## First steps: the workflow available today

<WorkflowVideo />

1. Install the CLI with `npm install -g specweave`, then follow the [quick start](/docs/getting-started).
2. Define one small outcome in a spec, including files, acceptance criteria and a test.
3. Claim the task, do the work, run the test and record its real evidence.
4. When you choose to transfer, run `specweave handoff`; use `specweave pickup` in the destination checkout after reviewing ownership and branch state.
5. Explore [Skill Studio](/docs/skills/skill-studio) if a repeated task would benefit from a tested skill.

In **SpecWeave 3.0.6**, `specweave auto-handoff on` enables silent local recovery checkpoints. It does not stop work at a usage limit, push a transfer, release task claims or authorize another worker. `pickup` does not apply those automatic checkpoints. See [checkpoint and handoff rules](/docs/guides/auto-handoff).

## Pilot walkthrough: remote Studio

<StudioOverviewVideo />

For an already provisioned pilot, use the operator-supplied private URL and current host-specific instructions:

1. Make sure you can reach the target machine: same network, SSH, or the approved tailnet.
2. Pair the browser to that Studio host with the provided scoped pairing flow. Being on the network is not enough.
3. Confirm the connection, project, native provider and account before submitting a small test request.
4. Inspect the actual output and any pending approval. A balance or usage percentage alone is not permission to run.
5. Reconnect and verify the same session on the same host. Keep project transfer explicit when moving work between tools or machines.

The operator provisions the private pilot; this guide does not imply a publicly available Studio download. [Discuss a pilot](/studio) with your engineering workflow, host requirements and evaluation criteria.

## For an enterprise evaluation

Begin with one repository, a small set of consenting engineers and a written success criterion. Measure accepted tasks, recovery effort, failed runs and review time. Keep tests, pilot activity and collected revenue distinct from adoption or ROI claims.

SpecWeave's task ledger is append-only **by CLI behavior and workflow convention**. It is an ordinary file and can be edited outside the CLI. Use your repository's review, access and retention controls when an auditable history matters. No cryptographic immutability or compliance certification is implied.
