# One ecosystem, three distinct jobs

**SpecWeave** keeps project intent and evidence in your repository. **vskill and Skill Studio** help you install and evaluate skills. **SpecWithCode** is the workspace on top: projects with a coordinator and workers on any provider, across your machines. Start with [the SpecWithCode overview](/docs/overview/studio/) for what it does; this page covers how the pieces connect.

<ProductMap />

SpecWithCode is not the app launched by `npx vskill studio`. That command opens **Skill Studio**, the skill development and evaluation workspace.

## The architecture

<Architecture />

| Layer | Responsibility | Boundary |
| --- | --- | --- |
| Browser | Display sessions, output and approvals | Browser connection state does not grant execution authority |
| Network route | Tailscale between machines in your fleet; for a browser or phone also the local network or an SSH tunnel | Reaching a host is not permission; SpecWithCode still requires pairing on every route |
| SpecWithCode runtime | Own host-local sessions, accounts, admission and recovery | Pair each host separately; do not copy credentials between accounts |
| Native agent | Execute a turn through its selected provider/account | Provider availability and approval rules still apply |
| Repository | Code, specs, task ledger and verification evidence | Git transports project changes; it is not a shared live session database |
| vskill | Inspect/install skills and run evaluations | Source trust and evaluation results require independent assessment |

### Connecting other machines

Machines that run workers for your coordinators join by their private Tailscale names. On the new machine, `fleet invite` publishes SpecWithCode inside your tailnet with Tailscale Serve and prints an invitation line; you paste it on the main machine under **Settings > Connections > Add a machine**. A Linux server or VPS on x64 or arm64 joins the same way. Step by step: [Add a machine](/docs/studio/add-a-machine) and [Linux worker](/docs/studio/linux-worker).

A browser or phone opening a SpecWithCode host can use one of several routes, and a host can keep more than one, using the first that answers:

| Route | When to use it | What you need |
| --- | --- | --- |
| Local network | The devices share a home or office network | Turn on network access on the host and pair with a one-time link |
| SSH | You can already SSH to the machine | The desktop app opens the tunnel and can start SpecWithCode on the remote host |
| Tailscale HTTPS | You are away from that network, or you want phone access | Both devices in the same tailnet; Tailscale Serve, never Funnel |

Tailscale **Serve** exposes a local service inside the private tailnet. **Funnel** is a different feature for public exposure; it is not SpecWithCode's remote-access design. See the [official Tailscale Serve documentation](https://tailscale.com/docs/features/tailscale-serve).

[SpecWithCode Connect](/docs/studio/connect), the hosted relay, is the default way to reach your machines from anywhere and from your phone. It is off until you sign in to it and includes 3 machines ([pricing](/pricing)).

### Providers and switching

SpecWithCode runs each provider's own agent with the sign-ins already on that machine: Claude Code, Codex, Cursor, Grok Build, OpenCode, Muse Code, Antigravity and Pi through their own integrations, and Gemini CLI, GitHub Copilot and other agents through the ACP Registry. Cursor is the exception: you sign in once inside SpecWithCode, or set `CURSOR_API_KEY`, and it runs as a local agent in the selected workspace through Cursor's SDK. SpecWithCode never starts Cursor cloud agents. Each thread picks its provider, model and effort. You can change provider inside a thread: SpecWithCode passes a budgeted selection of the conversation to the new agent, which continues in the same checkout. When a provider hits its usage limit, the project’s rule decides: switch to the fallback provider on its own (the default), offer the fallback, or wait for the reset.

### Optional components

**CLIProxyAPI** is optional. SpecWithCode can read pooled account usage from a CLIProxyAPI hub you already run and show it under **Usage → Limits**. Native Claude Code and Codex turns never pass through it. Routing personal subscription sign-ins through a shared proxy can conflict with a provider's terms, so check them before pooling accounts. **AnyModel** is likewise optional and only matters for API or local-model compatibility work.

### Security boundaries

- **Reachability is not authorization.** SpecWithCode stays bound to loopback and ignores Tailscale identity headers. Every origin needs its own pairing, even for a device already on the tailnet.
- **Restrict the tailnet.** The default tailnet policy lets every device reach Serve ports. Limit SpecWithCode's ports to your own devices with a grant, and do not share a SpecWithCode host to other tailnets.
- **Serve names are public.** Certificates for `*.ts.net` names appear in public Certificate Transparency logs. Choose machine names that do not identify you and keep them out of public repositories.
- **A usage hub key unlocks every pooled account.** An optional CLIProxyAPI hub's management key can make requests with any pooled account's token. Keep the hub on loopback with remote management off. SpecWithCode stores the key server-side, sends it only over https, loopback or a Tailscale address, and drops it when the hub URL moves.
- **Subscriptions follow provider terms.** SpecWithCode's native path runs the official Codex and Claude Code clients with their own sign-in. Routing subscription tokens through a proxy or pooling accounts to avoid limits can breach a provider's terms and risk suspension.

### Where data goes

Local-first describes where project files and runtime state live. It does not mean every request stays on the machine. Native coding agents and Skill Studio evaluations can contact their configured cloud model providers. Review those providers, account policies and any tools your skills invoke before using sensitive material.

Keep live worktrees, session databases and credential stores on their owning hosts. Use git and explicit handoff for portable code and task state. Private network access and SpecWithCode pairing are complementary controls, not interchangeable credentials.

### Inside a SpecWithCode host

The client sends authenticated, typed commands to the runtime on the machine that owns the session. A database transaction records events, projections, receipts and pending side effects in an outbox. Workers perform native-provider and Git operations and record their outcomes. **An accepted command is not the same as a completed side effect.**

Session state belongs to the native runtime; SpecWeave remains responsible for project intent, task ownership and acceptance evidence. An account pin and the session's host affinity remain meaningful even when several machines share a subscription. Adding hosts does not create extra provider quota: machines signed in to the same account share its limits, which is why we recommend one machine per subscription.

The optional [Jev / Decisions integration](/docs/guides/jev-system-one) handles bounded classifications in SpecWeave. Its model output is advisory: it does not grant permissions or prove a task passed verification.

Ask for an outcome in the chat. The agent manages the spec, task claims, tests and evidence through SpecWeave as it works. ## Under the hood: optional CLI deep dive

The following tutorial explains the commands an agent calls. Manual spec editing and task entry are not required steps in the SpecWithCode browser walkthrough.

<WorkflowVideo />

1. Install the CLI with `npm install -g specweave`, then follow the [quick start](/docs/getting-started).
2. Ask your coding agent for one small outcome with a clear way to verify it. The agent records the spec, files, acceptance criteria and test.
3. The agent claims the task, implements it, runs its test and records the real evidence. Inspect those records when you need the detail.
4. When you choose to transfer, ask the agent to hand off. It calls `specweave handoff`; the receiving agent calls `specweave pickup` after checking ownership and branch state.
5. Explore [Skill Studio](/docs/skills/skill-studio) if a repeated task would benefit from a tested skill.

Since SpecWeave 3.0.11, `specweave auto-handoff on` gives one heads-up at 95% of a usage window and keeps working (`suggest` mode); a turn that really hits the limit hands off by itself, and silent local checkpoints are saved between turns. Inside a SpecWithCode thread the hooks never steer the model, because the app switches provider itself. See [checkpoint and handoff rules](/docs/guides/auto-handoff).

## Walkthrough: remote SpecWithCode

<StudioOverviewVideo />

Install SpecWithCode on each machine that runs work, then connect them:

1. Put every machine in the same tailnet, and [add each worker machine](/docs/studio/add-a-machine) with `fleet invite` on it and **Add a machine** on the main one.
2. To open a host from a browser or phone, pair that browser with the host. Being on the network is not enough.
3. Confirm the connection, project, native provider and account before submitting a small test request.
4. Inspect the actual output and any pending approval. A balance or usage percentage alone is not permission to run.
5. Reconnect and verify the same session on the same host. Keep project transfer explicit when moving work between tools or machines.

## For a team evaluation

Begin with one repository, your team and a written success criterion. Measure accepted tasks, recovery effort, failed runs and review time. Keep tests, pilot activity and collected revenue distinct from adoption or ROI claims.

SpecWeave's task ledger is append-only **by CLI behavior and workflow convention**. It is an ordinary file and can be edited outside the CLI. Use your repository's review, access and retention controls when an auditable history matters. No cryptographic immutability or compliance certification is implied.
